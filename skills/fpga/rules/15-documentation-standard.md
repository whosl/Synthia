# SYNTHIA-FPGA-RULE-15：FPGA 标准集与文档编制规则

| 属性 | 内容 |
|---|---|
| 文档编号 | SYNTHIA-FPGA-RULE-15 |
| 适用范围 | engineering 项目的 FPGA 文档生成、修改、评审和交接 |
| 规范来源 | `references/standards/standards.json` 登记的 PDF 与检索转写；来源等级和缺失状态以该清单为准 |

## 1. 强制基准

工程项目的 PLDS 文档应以 GJB 9764-2020 为直接专用标准，按其文档种类、结构、正文顺序和裁剪规则编制。GJB 9764-2020 明确要求按 GJB 438B-2009 编制的文档，还应采用 GJB 438B-2009 对应附录；按需编制的 OCD、SSS、IRS、SSDD、IDD 采用 GJB 438B-2009 附录 A～E。Markdown 转写用于检索与生成；条文含义、正式符合性、裁剪和批准发生争议时，以仓库内 PDF 原文及授权质量/标准化角色决定为准。

GJB 9764-2020 对 GJB 438B-2009 是有日期引用，不得在未完成适用性评审时自动换用后续版本。

标准集各材料分工如下：

- GB/T 11457-2006 统一软件工程术语；
- GJB 2786A-2009 约束通用开发活动、支持活动和管理活动；
- GJB 438B-2009 提供 GJB 9764-2020 指定的通用文档结构；
- GJB 5235-2004 约束配置标识、配置控制、状态记实、评价、发行和交付；
- GJB 9433-2018 约束 PLDS 测试目的、级别、过程、类型和方法；
- GJB 9764-2020 约束 PLDS 文档种类、结构和内容。

GJB 9432-2018 的完整可信文本尚未取得，GB/T 8566-2022 全文也未取得和完成适用性评审；二者在 `standards.json` 中必须保持 `missing`。依赖其完整条文的开发、配置、测试或符合性判断一律 fail-closed：保留章条和活动，标为“阻塞/待受控文本复核”，不得根据残件、相似标准、OCR 猜测或模型记忆宣称满足。公开预览重建件可支撑候选规则提取，但不得称为发行机构权威电子原件。

每份正式类型文档均应包含：封面信息、修改页、目录、正文，以及被正文引用的附录。封面信息至少写明文档标识及版本、密级或数据分类、日期、文档名称、编制单位、编写、审核、批准。未知内容写“待确定”或“待授权角色填写”，不得虚构姓名、签名、批准日期、密级或批准状态。

## 2. 文档选择与阶段映射

根据项目阶段和测试级别选择文档，不要把不同用途的内容塞进一份无类型的“说明”：

- 研制依据和顶层任务要求：PLDSDTD；
- PLDS 配置项需求：PLDSRS；
- 概要、详细和验证设计：PLDSDD；
- 仿真测试：PLDSSTP、PLDSSTD、PLDSSTR；
- 配置项或系统确认/实物测试：PLDSVTP、PLDSVTD、PLDSVTR；
- 其他计划、产品、版本、使用、总结、配置管理和质量保证文档按 4.1 和第 5 章选择。

其中 SDP、SCMP、SQAP、STrP、SPS、SVD、SCMR、SQAR 应分别读取 GJB 438B-2009 附录 G、H、I、K、R、S、AA、BB；不要只写文档名或一段自由说明。

测试计划、测试说明、测试报告是三个不同的配置对象：计划定义策略和范围，说明定义可复现用例与判据，报告记录精确版本上的实际执行和问题。测试内容还应按 GJB 9433-2018 区分级别、过程、类型和方法，覆盖正常/异常、边界、接口、时序、强度、余量、安全性和功耗等适用项；未覆盖项逐项说明。不得用计划冒充说明或报告，不得把 exploratory 运行写成批准测试结论。

## 3. 正文章条与裁剪

正文必须采用对应规范性附录的章条顺序。附录标题中的 `X`、`Y` 要替换为项目内唯一、稳定的真实编号。没有内容的章条仍保留原位置，并明确写“本章无内容”或“本节无内容”，随后说明事实依据和影响。

合并文档时选定主文档，在注释中列出被合并文档及对应章条，并保持全部要素完整。拆分文档时，每份均满足通用结构，并在其中一份说明拆分关系。裁剪、合并或拆分只能记录为候选建议；正式决定必须有适用对象、依据、理由、风险、替代证据、批准角色和日期。

## 4. 事实、追踪与证据

每条任务要求、需求、设计模块、测试项和测试用例使用唯一标识。至少建立 PLDSDTD → PLDSRS → PLDSDD → RTL/TB → 测试项/用例 → 测试结果的双向追踪。需求表述应可验证，接口应写方向、位宽、初始/复位值和时序语义，设计应写时钟域、资源、可靠性、安全性和可测试性，测试用例应写需求、先决条件、输入、预期结果、判据、终止条件、步骤、假设和约束。术语优先采用 GB/T 11457-2006；不得把 `candidate`、ToolRun、工作区修订或门禁快照未经授权就称为配置项、基线、验证或确认结论。

候选产物进入评审或交付前，应按 GJB 5235-2004 唯一标识版本和关系，记录状态及更改，确保输入哈希、生成/验证工具、基线成员和授权动作可追溯。工作区文件、git 提交和 Core 快照只是实现机制；只有项目定义并履行配置标识、控制、评价和授权程序后，才能形成受控配置项或基线。

报告只引用真实 ToolRun、日志、波形、覆盖或审查证据。记录被测版本/哈希、环境、命令、结果、偏差和问题；未执行项写“未执行”及原因。缺板卡、管脚、电气、仪器或批准输入时，确认测试属于“阻塞”，不是“不适用”，不得生成虚假的 PLDSVTR 或交付结论。

## 5. 输出前检查

提交候选前逐项检查：`standards.json` 的材料状态已读取；文档类型正确；适用的 GJB 9764-2020 与 GJB 438B-2009 附录已读取；术语与 GB/T 11457-2006 一致；开发和支撑活动没有绕过 GJB 2786A-2009；配置记录满足 GJB 5235-2004 的适用要求；测试覆盖按 GJB 9433-2018 展开；GJB 9432-2018 与 GB/T 8566-2022 缺口已显式阻塞；封面/修改页/目录齐全；正文编号和顺序对应附录；裁剪章条仍在原位并有理由；所有引用路径和版本存在；追踪无孤立项；结果与原始证据一致；未知事实未被猜测；candidate、diagnostic、exploratory、approved 状态没有混用。
