# FPGA 产物状态、证据与收尾约定

| 属性 | 内容 |
|---|---|
| 规则编号 | SYNTHIA-FPGA-RULE-60 |
| 版本/状态 | v0.1 / candidate |
| 适用对象 | 全部 FPGA 技能的产物登记、证据引用与用户可见总结 |

## 1. 产物状态约定

- 技能产出一律登记为候选 `ArtifactRevision`（`candidate`）或诊断产物（`diagnostic`）：
  - `candidate`：需求摘要、架构契约、行为规格、寄存器契约、RTL/TB 源码、约束文件等待评审内容；
  - `diagnostic`：ToolRun 记录、编译检查报告、仿真运行报告、修复报告等基于工具证据的分析内容。
- `candidate`/`diagnostic` 都不是通过结论。`in_review`/`approved`/`rejected` 由 Core 状态机经人类门禁驱动，技能不得把候选或诊断结果冒充为已批准结论。
- 每个候选修订登记时必须带内容哈希与来源关系（parent revision / source ids）；修订被拒绝后通过新修订继续，不原地改写。

## 2. 证据要求

- 涉及工具行为的结论必须引用 EvidenceManifest 条目（名称、URI、SHA-256），不接受无证据的"应当/大致/可能"式结论。
- 报告中的 PASS/FAIL 必须标注其证据范围（哪个 ToolRun、哪个输入哈希、哪个日志条目）。
- 失败证据（日志、报告、未收敛记录）必须完整保留，禁止删除。

## 3. 用户可见收尾约定

每个 FPGA 技能在创建、修改、检查或阻塞候选产物后，由 Runtime 在最终回复前用一段简洁中文向用户说明：本轮做了什么、改了什么、还差什么、下一步可以做什么。

推荐格式：

```text
任务总结：本轮……（一句话结论，用动词开头说明结果状态：已完成候选 / 部分完成 / 等待补充 / 失败）。

做了什么：
- ……（2-4 条可在文件/证据层面验证的事实）

下一步建议：
- ……（每条对应用户可直接说出口的下一句请求）

需要补充的信息（如有）：
- ……
```

要点：

- 不暴露内部技能名、能力 ID、规则文件名、Schema 名等实现细节；
- "下一步建议"必须来自真实产物状态：能提交的检查、能修改的候选、能继续的阶段才能成为下一步，不伪造入口；
- 真实失败必须直说：哪个文件没登记、哪个 ToolRun 返回失败、缺哪个输入；
- 总结中提及 post-mvp 能力（实现、码流、下载、波形导出）时必须标注未启用；
- 总行数控制在 8 行以内；确实无内容时用一句话完结。
