# FPGA 技能路由规则

| 属性 | 内容 |
|---|---|
| 规则编号 | SYNTHIA-FPGA-RULE-00 |
| 版本/状态 | v0.1 / candidate |
| 适用对象 | `skills/fpga` 技能包内全部技能的路由决策 |

## 1. 总原则

1. 优先选择最窄、产物最明确的技能。
2. 需求模糊、缺少验收标准时先走 `fpga-intake`；需求已明确（含具体模块名、功能描述或已有代码参考）时直接进入对应实现类技能。
3. 用户在 TaskPackage 中明确指定某个技能且与请求一致时，直接进入该技能。
4. 路由决策是平台内部行为；路由只产生 Task（任务建议），不产生任何批准、基线或发布动作。

## 2. 执行语义边界（必须遵守）

- 所有技能在 Synthia Agent Runtime 中运行，只做**需求理解、规划、候选生成、分析与交接**。
- 技能产出统一为候选 `ArtifactRevision`（`candidate`）或诊断产物（`diagnostic`），经版本化 Core API 登记；技能不持有批准、基线、发布、硬件写权限。
- 常规 Vivado 操作只通过强类型 Connector 能力交接（见 `30-toolchain-and-tcl-boundary.md`）；任何技能不得直接执行工具命令、脚本或任意 Tcl。
- 面向用户的进度表述只描述工程阶段（如"正在生成 RTL 候选""正在进行编译检查"），不暴露内部技能名、能力 ID 或运行时细节。

## 3. 协议时序敏感模块判定标准

满足以下任一条件的模块视为**协议时序敏感**，其关键契约未冻结时不得直接进入 `fpga-rtl-build`：

1. 接口存在 launch/sample 边沿语义（如 SPI 模式、SD 命令/数据边沿）；
2. 存在相位次序（phase ordering）要求的多阶段事务；
3. 片选/使能信号有明确生命周期约束（断言、保持、释放窗口）；
4. 命令/响应边界需要按协议精确划分；
5. 需要上电/初始化序列（如 SPI Flash init、SD 卡初始化、UART bootloader）。

关键契约指：端口/参数语义、边沿语义、相位次序、片选生命周期、命令/响应边界、初始化步骤。以上任一项只能靠猜测补全时，必须先回退到 `fpga-intake`、`fpga-architecture` 或 `fpga-behavior-and-wave-plan` 补齐上游定义。

## 4. 路由表（按用户意图）

- 需求含混、缺验收、不知从何开始：`fpga-intake`。
- 需求已明确且需要写代码：
  - 含 RTL 实现：`fpga-rtl-build`；
  - 含 TB 源码生成：`fpga-tb-write`；
  - 同时含 RTL + TB：先 `fpga-rtl-build`，再 `fpga-tb-write`；
  - 含仿真运行：已有 RTL/TB 候选时走 `fpga-sim-run`；缺 TB 时先 `fpga-tb-write`；
  - 含 XDC/约束/管脚分配：`fpga-xdc-gen`；缺硬件事实时它会以缺失信息失败并给出补全路径（提取硬件事实 → 生成板级 top → 生成约束）。
- **多模块/协议类任务必须先架构后 RTL**：涉及 2 个以上相互通信的子模块、协议初始化序列、CRC/包组装/握手/多时钟域数据通路，或顶层端口与子模块边界尚未定义时，先 `fpga-architecture` 再 `fpga-rtl-build`。禁止在架构未定稿时直接生成整个系统的 RTL。
- **RTL 生成按模块逐一进行**：`fpga-rtl-build` 一次调用只产出一个模块；架构输出的模块列表逐个交接，前一个模块候选登记完成后再交接下一个。
- 中间技能按需触发：
  - 多模块拆分、总线接口、CDC 策略：`fpga-architecture`；
  - 寄存器映射、CPU 总线接口（AXI-Lite/APB）、控制面：`fpga-register-spec`；
  - 行为规格、FSM 规则、不变量、波形检查点：`fpga-behavior-and-wave-plan`；
  - 综合约束、引脚分配：`fpga-xdc-gen`；
  - 板级管脚/时钟/电气事实缺失：`fpga-hw-manual-extraction`。
- 简单计数器/分频器/单模块/数据通路：直接 `fpga-rtl-build`，使用合理默认端口与复位策略，并在 `doc/spec/behavior_spec.md` 记录假设。
- 只做编译检查：优先 `fpga-compile-and-repair`（tool-first，尽量不改代码）。

## 5. 生成类与编辑类的分界

**必须经技能生成候选**：
- 从零生成新 RTL 模块：`fpga-rtl-build`；
- 修改现有 RTL 的设计意图（重写状态机逻辑、改变接口协议、调整数据通路）：`fpga-rtl-build`；
- 从零生成或按修改后 RTL 重生成 TB：`fpga-tb-write`。

**可直接作为候选修订的编辑**（在 Runtime 候选工作区中作为新 ArtifactRevision 登记，无需专项技能）：
- 为已有 RTL 加注释、整理格式；
- 修复 RTL 语法错误（敏感信号缺失、位宽不匹配）；
- 修改参数值、常量定义、端口宽度；
- 添加断言/覆盖组。

**禁止**：在 Runtime 主流程中绕过技能直接生成完整的、可综合的 RTL 模块正文（含完整状态机、数据通路、接口实现）。

## 6. 候选质量闸门与重复失败处理

技能产出的源码候选进入登记前必须过质量闸门：

| 批次质量 | 闸门行为 |
|---|---|
| 完整实现、无 stub | 登记为 `candidate`，该阶段结束 |
| 完整实现声明但含 stub 段落 | 不登记，进入补全重试 |
| 部分实现（partial） | 不登记，提取 stub 清单后补全重试 |
| 缺输入（needs_input） | 不登记，收集缺失信息并升级人类 |
| 无产物或内部错误 | 不登记，报告原因 |

- stub 判定：`// ...`、`// omitted`、`// TODO`、`// FIXME`、`// TBD`、`// stub`、空 `begin...end` 块、被注释掉的完整 `always`/`case`/`assign` 段落等。
- 禁止择优登记：不得从 partial / needs_input / 含 stub 的批次中挑"看起来还行"的单个文件登记。质量判定以批次为单位。
- 补全重试不得原文重发任务：必须先从上次输出提取 stub 段落清单，注入补全指引后再重试。
- 连续 2 次"有内容但质量不达标"后停止自动重试，向人类说明质量问题并给出建议（拆解任务、补充约束、回退上游技能）；3 次以上一律要求人类介入决策。
- 编辑类任务重试失败时，可直接以候选修订方式完成基础编辑，不得卡死流程。

## 7. 阶段可选策略（默认最小动作）

- 用户只要求 RTL 时，完成 RTL 候选后停止；TB、编译检查、仿真、约束作为后续可选任务建议展示。
- 不自动运行编译检查或仿真：仅当用户本轮明确要求，或选择了前序交接中的对应选项时才触发。
- 用户要求"完整流程/完整验证"时，按 RTL → TB → 编译检查 → 仿真 → 约束推进；各阶段产物均为候选/诊断状态，门禁通过与批准由人类流程决定。

## 8. 板级顶层引导

用户表达板级意图（LED、KEY、时钟、约束、上板等）但 `rtl/` 下没有板级顶层时：

1. 硬件事实已完备：建议经 `fpga-rtl-build`（板级信号已知）或 `fpga-architecture`（需规划顶层结构）生成 `rtl/top.v` 候选。硬件事实“已完备”仅指以下两种情形之一：
   - Core 已登记 `doc/hw/extracted_facts.json` 且 `status=complete`，逐条事实带 `source_ref` 与 `evidence_kind`；
   - 用户提供明确的、等价的可追溯板级契约（如板卡原理图/手册条目、引脚分配表原文）。
   板卡配置文件（如 config.json）只能提供上下文线索，不能单独作为管脚名、时钟或电气参数的物理证据；仅有配置而无上述登记事实或用户契约时，按第 2 条处理。
2. 硬件事实未完备：建议先 `fpga-hw-manual-extraction` 提取事实，再生成 `top.v`，再生成约束。不要在没有板级信号名的情况下硬编 top。
3. 纯内部模块意图（ALU、FIFO、协议引擎等）：不主动建议生成 `top.v`，除非用户明确要求。
