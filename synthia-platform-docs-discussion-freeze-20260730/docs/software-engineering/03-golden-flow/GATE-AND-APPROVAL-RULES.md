# Synthia 阶段门与人工批准规则

| 属性 | 内容 |
|---|---|
| 文档编号 | SYNTHIA-FLOW-003 |
| 版本/状态 | v0.2 / 讨论冻结候选，待正式评审 |
| 上游 | SYNTHIA-FLOW-001、SYNTHIA-FLOW-002 v0.2、SYNTHIA-ARC-002 |
| 核心约束 | Agent 只能生成 candidate；只有授权人类可以批准、拒绝、豁免、建立基线和验收 |

## 1. 目的

本规则定义 G1～G9 的提交、确定性检查、专业审查、批准、拒绝、带行动批准、重新打开和失效传播，保证人类批准具有明确对象、证据和责任边界。

## 2. 决策类型

| 决策 | 含义 | 后续状态 |
|---|---|---|
| `approve` | 所有阻断准则满足，接受指定快照形成批准阶段结果 | 修订 `approved`；里程碑门建立/更新 B0～B4 |
| `reject` | 存在阻断缺陷或不同意技术方案 | 制品 `rejected` 或退回 `candidate` 新修订 |
| `approve_with_actions` | 仅有不阻断本门的后续行动，且截止门/责任清楚 | 制品 `approved`，行动进入登记册 |
| `request_changes` | 需要修订但不否定目标 | 当前审查关闭，新候选版本重新提交 |

`approve_with_actions` 不能绕过需求冲突、关键安全语义未定义、严重静态问题、关键 CDC、DRC/STA 失败、测试失败、配置不一致或缺少正式输入等硬门禁。

## 3. 审批主体和分离

| 门 | 最低批准角色 | 生成者自批限制 |
|---|---|---|
| G1 | 项目/系统需求负责人 | 需求 Agent 和起草人不能代签 |
| G2 | PLDS 设计负责人 + 系统需求代表 | 派生需求影响需上游确认 |
| G3 | PLDS 设计负责人；安全关键时增加验证/安全角色 | 设计生成者不能单独批准自身关键设计 |
| G4 | PLDS 设计/代码审查 + 验证 + 配置角色 | RTL Agent、验证 Agent 均无批准权 |
| G5 | FPGA 实现负责人 + 验证/质量复核 | Connector 只能提供事实 |
| G6 | FPGA 实现负责人 + 质量/时序复核 | strategy 操作者不能独立接受违规 |
| G7 | 验证负责人 + 质量角色 | 设计者自测不能替代确认测试批准 |
| G8 | 硬件/系统 + 配置 + 发布授权角色 | 码流生成账号无发布权 |
| G9 | 项目/需方 + 质量 + 配置 | Agent/Connector 不能代替验收签署 |

原型期允许同一自然人兼任多个执行角色，但每个关键门必须记录不同的“生成身份”和“复核/批准身份”。真实项目的独立性按完整性等级和单位制度提高。

## 4. 通用门禁流程

1. 提交者选择固定制品版本并创建 Gate Submission；
2. 平台冻结提交快照，计算清单、哈希、追踪和未关闭问题；
3. 确定性门禁执行 Schema、状态、覆盖、工具结果和配置一致性检查；
4. 不满足硬门禁时自动拒绝进入人工批准队列，并给出客观缺口；
5. 专业审查人查看差异、原始证据、风险、豁免和 Agent 谱系；
6. 审批人使用个人身份作出决策并填写理由；
7. 平台原子地记录决策、签署对象、版本/哈希和时间；
8. 批准时建立 `ApprovedGateResult`；G1/G3/G4/G7/G9 同时建立 B0～B4，其他门不建立“候选基线”；拒绝/修改时保留提交快照并创建修订任务；
9. 行动项、通知和下阶段入口状态自动更新。

## 5. 各门硬门禁

| 门 | 硬门禁摘要 | 不阻断但必须跟踪的典型项 |
|---|---|---|
| G1 | 来源/数据域明确；系统需求唯一、可验证；阻断冲突关闭；关键风险有处置 | 后续板卡候选、非关键环境细节 |
| G2 | 每项 PLDS 需求有来源/派生理由；派生反馈；验证方法；双向追踪无孤立 | 后续工具小版本、非关键参数优化 |
| G3 | 全需求分配；接口/状态/时钟复位/异常/约束无编码歧义；安全关键设计专项审查 | 不影响 RTL 的版式/图示改进 |
| G4 | B1 approved；RTL/TB/XDC/追踪/manifest 齐全；绑定同一冻结快照的编译/Lint/必要预综合 CDC `gate_check` 通过；规定的严重静态和关键 CDC/RDC 为 0；代码审查关闭 | 经批准的非关键告警；尚未选板时的板级 XDC 行动须在首次正式 G6 前关闭 |
| G5 | part/工具/strategy 受控；综合成功；综合网表关键结构与设计一致；资源/综合问题处置 | 非关键优化建议 |
| G6 | 实现成功；DRC/STA/未约束对象满足批准阈值；物理/时序例外有依据；结果可重现 | 有量化余量且不影响要求的优化项 |
| G7 | 适用测试全部执行；需求通过；覆盖门禁满足；高严重度问题关闭；排除项批准 | 中低问题的延期措施和接受 |
| G8 | 码流来自批准实现；哈希/目标匹配；下载/板测通过；FCA/PCA 无阻断缺口 | 经批准的非交付演示限制 |
| G9 | 合同/项目交付清单完整；批准/风险/问题/质量/配置结论齐备；接收方签署 | 维护期改进建议 |

详细的字段与制品组合由 ARTIFACT-CONTRACTS 和项目 Gate Profile 提供。项目只能提高硬门禁，降低时需要正式裁剪批准。

## 6. 批准记录契约

每次决定至少记录：

- `approval_id`、项目、门和流程实例版本；
- 被审对象及版本/哈希、提交清单哈希；
- 审批人个人身份、角色和授权依据；
- 决策、理由、问题/风险/豁免引用；
- 确定性检查结果和原始证据链接；
- 时间、签署方式、客户端/服务审计摘要；
- 适用时的行动、责任、截止门和残余风险；
- 由该决定建立的 ApprovedGateResult ID，以及适用时的 B0～B4 ID。

普通用户、Agent 和构建账号不得修改批准记录。撤销批准必须创建新的撤销/失效记录，不能删除历史。

## 7. 豁免和偏差

豁免至少包含规则/要求、对象、客观证据、原因、影响、补偿措施、有效范围、失效日期、回归要求和批准人。豁免不能把失败结果改名为通过；它只能由有权角色接受已分析的偏差，并在报告中单独统计。

以下项目默认不可在普通项目层豁免：未批准输入执行正式验证、伪造/缺失原始工具证据、码流与输入基线无法追溯、未授权人员批准、敏感数据出域、未知目标器件下载。

## 8. 重新打开与失效

以下事件触发门禁重新评估：

- 批准需求、设计、RTL、XDC、测试或工具配置变化；
- 器件 part、Vivado 主/次版本或实现 strategy 变化；
- 新发现缺陷影响批准结论；
- 追踪关系断裂或证据哈希不匹配；
- 数据域、完整性等级、交付范围或标准裁剪变化；
- 测试环境/板卡变化导致结果不可比。

平台沿追踪关系先把尚待判断的关系/批准有效性投影标为 `review_required`；有客观依据表明当前结论不能继续用于新放行时标为 `invalidated`。审批人确认影响为零时创建新的“无影响确认”记录；否则回到最早受影响门并执行规定回归。不得把两种状态作为同义词互换。

## 9. 运行批准与工程批准分离

允许 Connector 执行一次工具任务，不等于批准任务结果进入基线。高影响运行可要求“执行批准”，工程结果仍需后续门禁批准。例如：

- 探索性综合：允许执行，但 `run_class=exploratory`，不得进入门禁；
- G4 门禁检查：输入为冻结 GateSubmission，`run_class=gate_check`，只能支持该提交；
- 正式综合：输入必须为 B2，`run_class=formal`，运行任务获授权；
- 生成码流：要求批准 G6/G7 阶段结果和发布前执行授权；
- 下载器件/修改 VIO：要求目标硬件、操作者和操作范围批准。

## 10. 人工界面最低要求

Web 审批界面应同时显示：当前门、输入基线、变更差异、未关闭问题/风险、追踪缺口、确定性检查、原始报告、Agent/工具谱系和决定影响。禁止只显示 Agent 的“建议通过”摘要。

## 11. 审计与度量

平台报告提交次数、首次通过率、拒绝原因、审批耗时、豁免、门禁回退、批准后缺陷和失效传播。效率指标不能隐藏失败提交或以减少人工审批次数作为单一优化目标。
