# 完整性、安全、部署与审核基线说明

## 1. 为什么需要先区分四个概念

### 1.1 完整性/安全关键等级

它回答的是：“这个 FPGA 功能失效后，后果有多严重？”后果越严重，需求和测试就越严格，验证独立性、覆盖率、评审深度和配置控制也越强。等级不是按代码行数或器件大小决定，而应从所属系统的危害分析和失效影响向下分配。

当前尚无真实装备系统和危害分析，因此不能负责任地给示范 UART 指定正式完整性等级。第一期建议采用“非交付原型、严格证据流程”：不宣称正式等级，但完整演练需求、设计、代码、验证、评审、配置和问题闭环，避免以后推倒重来。

### 1.2 保密/部署网域

它回答的是：“哪些数据可以到哪里、由谁访问？”这与功能安全不是一回事。一个非安全关键模块也可能包含涉密接口和设计数据；一个安全关键模块也不必然涉密。

一期建议：平台在本机或单位内私有网络部署；工程数据、提示词、检索片段和模型输入输出不出批准网域；默认禁止外部模型 API；采用最小权限、项目隔离和完整审计。

### 1.3 模型来源与可复现性

模型来源决定数据外发风险、许可证、供应链和输出漂移。平台应记录模型名称、发布方、版本/权重摘要、推理参数、系统提示模板版本、知识库版本和本次上下文清单。

一期建议：使用可在本地或私有化环境部署的模型；工程数据默认不用于训练；模型只生成候选成果，确定性工具和人工审核共同决定是否进入基线。

### 1.4 审核角色

审核角色解决责任分离问题。最低需要区分：需求批准、FPGA 设计批准、验证结论批准、配置发布批准。原型期允许一人兼任多个执行角色，但关键基线不应由产物生成者单独自批。

## 2. 一期建议控制档

| 控制项 | 一期建议 |
|---|---|
| 正式完整性等级 | 未定级；明确标注“非交付示范工程” |
| 工程严谨度 | 按完整生命周期保存证据，执行双向追踪和阶段门 |
| 部署 | 本机/单位内私有化，默认无外部推理调用 |
| 模型 | 本地可部署、版本固定、摘要可验证 |
| AI 权限 | 只创建候选需求/设计/代码/测试，不可自行批准和发布位流 |
| 最低复核 | 需求/设计/代码由 FPGA 领域人员复核；测试结论由另一审核身份复核 |
| 发布 | 配置管理员或项目负责人进行二次确认并记录产物哈希 |
| 数据 | 示例工程可公开；真实工程进入前重新开展数据分级和威胁分析 |

## 3. 真实项目接入时必须补充

1. 所属系统的危害分析、失效后果和完整性等级分配；
2. 项目密级、数据分类、跨网交换和审计保留要求；
3. 经批准的模型、算力环境和软件供应链清单；
4. 需方、设计、验证、质量、配置和安全责任人的正式任命；
5. 对应等级下需要的独立验证、覆盖率、故障注入和评审强度。
