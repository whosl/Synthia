# 生存周期、阶段门与交付物

## 1. 总体方法

采用“阶段门控制基线、阶段内迭代完善”的混合过程。每个门均要求入口资料齐备、规定活动完成、问题有明确处置、授权角色批准；未满足门禁的成果不能自动进入下一阶段。

## 2. 目标 PLDS 产品阶段门

| 阶段门 | 核心活动 | 最小工作产品 | 退出条件 |
|---|---|---|---|
| G0 项目准备 | 范围、适用标准/裁剪、角色、数据域、工具/器件/板卡、配置/质量/风险准备 | 项目档案、来源包、计划、裁剪记录、角色授权、环境候选 | 项目负责人批准启动；不形成产品技术基线 |
| G1 系统需求批准 | 可行性、器件/环境/接口、安全可靠性、确认与交付要求分析 | 开发技术要求、系统需求、可行性/风险、开放问题处置 | 系统需求明确、可验证、风险已处置；建立 B0 |
| G2 PLDS SRS 和派生需求批准 | 功能、性能、接口、约束、完整性及派生需求分析 | PLDS SRS、派生需求、系统—PLDS 追踪、验证方法 | 每项需求有来源或批准派生理由；形成冻结批准阶段结果，不新增 B 编号 |
| G3 结构/详细设计批准 | 单元划分、接口、数据/控制流、RTL 微架构、FSM、时钟复位、CDC/RDC、存储/IP 和约束策略 | 结构设计、详细设计、约束设计、需求分配、设计评审 | 设计足以无歧义编码，关键边界闭合；建立 B1 |
| G4 RTL、TB、约束及代码审查批准 | RTL/TB/XDC 候选生成；对冻结快照执行编译、Lint、必要预综合 CDC/RDC、仿真、追踪和代码审查 gate_check | RTL、IP 封装、TB/参考模型/断言、XDC、静态/仿真报告、审查记录、构建清单 | 严重问题清零或按规则处置，授权人类批准；建立 B2 |
| G5 综合和网表结构批准 | 使用批准 B2 执行 formal 综合、综合后 DRC/CDC 和关键结构检查 | 原始日志、综合网表/DCP、资源/约束/结构报告、运行 manifest | 综合成功、关键结构保留、结果可重现；形成冻结批准阶段结果 |
| G6 布局布线、DRC、STA 批准 | 使用批准 G5 结果执行优化、布局、布线、实现后 DRC/STA、资源/功耗和适用时序分析 | 检查点、DRC、STA、利用率、功耗及偏差/豁免记录 | 规定门禁满足或偏差获批；形成冻结批准阶段结果 |
| G7 确认测试通过 | 在批准配置上执行需求驱动测试、覆盖、故障注入、回归和必要的门级/时序测试 | 测试运行、覆盖、失败/问题/回归、确认测试报告 | 适用需求有有效通过证据；建立 B3 |
| G8 码流、板测和配置审核通过 | Vivado 与 Board/Lab Connector 从批准结果生成码流并执行下载、启动、ILA/VIO、板测及配置审核 | 码流/哈希、下载和板测原始记录、配置审核、产品清单 | 码流可追溯，板测满足判据；形成冻结批准阶段结果，不建立候选基线 |
| G9 验收交付 | 验收、交付重现、签署、归档和运行维护移交 | B4、交付包、接收记录、用户/维护资料、质量/配置总结 | 验收方签署，交付完整可校验，建立正式产品基线 B4 |

## 3. 平台必须固化的门禁能力

1. 入口/出口准则可配置且版本化；
2. 工作产品与其来源、工具版本、操作者/智能体、时间、哈希关联；
3. AI 候选产物与批准后的基线产物明确区分；
4. 评审问题、纠正措施、豁免和批准记录不可被普通用户覆写；
5. 需求、设计、实现、验证之间可双向导航并自动计算覆盖率；
6. 失败活动不能伪装成成功，重新运行保留完整谱系；
7. 码流生成、下载和发布分别受控，且可追溯到源代码、约束、IP、工具、器件、实现和验证基线；
8. Connector 的 `succeeded` 只说明操作完成且必需输出存在，不等于 G5～G9 工程结论获批；
9. 规划覆盖、执行覆盖和需求通过率必须分别计算，禁止用关系已规划代替测试已通过。

## 4. 交付物裁剪原则

GJB 9432 附录 A 的技术文档清单应作为目标 PLDS 产品的起始集合，不允许因平台“自动生成”而直接删除。确需裁剪时必须说明：裁剪对象、适用项目、理由、风险、替代证据、批准人和批准日期。
