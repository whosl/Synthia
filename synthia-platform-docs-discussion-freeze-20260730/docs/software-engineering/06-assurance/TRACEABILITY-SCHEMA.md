本文件保留便于阅读的追踪概览。实体、关系、状态、不变量、覆盖率和 API 的权威定义见 `../03-golden-flow/TRACEABILITY-DATA-MODEL.md`；二者冲突时以该文件批准版本为准。

## 1. 追踪链

```text
业务目标
  ↕
系统需求
  ↕
PLDS 需求（含派生需求）
  ↕
结构/详细设计单元
  ↕
RTL / IP / 约束
  ↕
验证项 / 测试用例 / 覆盖点
  ↕
仿真 / 综合 / 实现 / DRC / STA / 测试运行
  ↕
原始证据 / 覆盖结果 / 问题 / 批准结论
  ↕
码流 / 下载 / ILA/VIO / 硬件验证 / 交付包
```

## 2. 最小对象字段

每个追踪对象至少包含：稳定 ID、标题、正文、类型、所属项目、版本、状态、安全关键标记、来源、责任人、验证方法、创建/修改时间、批准记录和配置基线。

追踪关系至少包含：源 ID、目标 ID、关系类型、理由、创建者、状态、版本和审查记录。

## 3. 关系类型

| 关系 | 含义 |
|---|---|
| `derived_from` | PLDS/派生需求来自上游需求或 Source，派生项须反馈上游评估 |
| `refines` | 下层需求/设计细化上层对象，但不替代上层对象 |
| `allocated_to` | 需求分配给设计单元 |
| `implemented_by` | 需求/设计由 RTL、IP 或约束实现 |
| `verified_by` | 需求/设计/实现由验证项或测试用例验证 |
| `executed_in` | 验证项由具体 ToolRun 执行 |
| `produces` | 执行活动生成产物 |
| `supports` | Evidence 支撑需求、门禁或结论 |
| `contradicts` | Issue/Evidence 发现冲突或失败 |
| `affected_by` | 对象受到变更或问题影响 |
| `submitted_as` | ConfigurationSnapshot 提交为 GateSubmission |
| `decided_by` | GateSubmission/Baseline 由 ApprovalRecord 决定 |
| `establishes` | ApprovalRecord 建立 ApprovedGateResult 或 Baseline |
| `member_of` | 制品或证据进入批准基线 |
| `supersedes` | 新版本替代旧版本 |
| `extracted_as` | 批准制品/证据提取为知识条目 |

## 4. 覆盖率口径

“100% 追踪覆盖率”必须拆分状态和分母，禁止只报一个模糊总数：

1. 上游覆盖率：每项已批准 PLDS 需求均有系统需求来源，派生需求除外但必须有派生理由和上游反馈；
2. 设计覆盖率：每项已批准 PLDS 需求至少分配到一个已批准设计单元；
3. 实现规划覆盖率：每个需要实现的设计单元关联候选或批准 RTL/IP/约束，并分别统计状态；
4. 验证规划覆盖率：每项已批准 PLDS 需求至少关联一个验证项和明确通过准则，不表示已经执行；
5. 验证执行覆盖率：应执行验证项中已有正式运行的比例，失败运行计已执行但不计通过；
6. 需求通过率：应验证需求中具有批准通过结论和有效证据的比例，排除和未执行项单列。

还必须报告反向孤立项：无需求依据的设计/RTL/约束/测试、无测试依据的执行结果，以及已经失效但仍被引用的对象。

## 5. AI 生成关系的控制

智能体可提出追踪关系，但必须标记为候选；候选关系不能混入批准关系口径。只有通过规则检查并经授权角色批准后，才能进入正式基线。报告必须同时显示候选、批准、执行和通过四类口径，且不得把任何规划覆盖率表述为测试已通过。
