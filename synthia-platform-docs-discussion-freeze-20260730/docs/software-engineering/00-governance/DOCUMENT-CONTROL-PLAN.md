# 文档控制计划

## 1. 状态模型

人类文档视图使用：`工作草案` → `讨论冻结候选`/`待评审` → `已批准`，以及 `修订中`、`已废止`。平台数据层按实体使用独立状态机：文档 ArtifactRevision 映射为 `candidate/in_review/approved/rejected/superseded/invalidated`；`review_required` 是关系或批准有效性投影的待复核状态，不与 `invalidated` 同义；Baseline 只能由批准创建，不存在 candidate Baseline。`修订中`表示从批准版本派生了新的 candidate，不允许原地修改 approved 内容。

只有被明确批准且当前有效的版本才能作为正式设计、实现、验证和验收依据。AI/Agent 生成内容默认是工作草案，不能自动批准自身产物；工具运行成功也不能自动把文档或工程结论改为 approved。

## 2. 文档头最小字段

每份受控文档至少包含：文档编号、标题、所属产品、版本、状态、作者、审核人、批准人、发布日期、适用范围、上游依据、变更摘要。

建议编号规则：

```text
SYN-{类别}-{序号}

类别：PLAN / REQ / DES / IF / VVP / TST / CM / QA / RM / OPS / REP
示例：SYN-REQ-001 软件需求规格说明
```

目标 PLDS 项目实例使用独立前缀，避免平台需求与被生成产品需求混淆：

```text
{项目代号}-SYS-REQ-####
{项目代号}-PLDS-REQ-####
{项目代号}-DES-####
{项目代号}-RTL-####
{项目代号}-VER-####
{项目代号}-TST-####
```

## 3. 变更控制

基线后的变更必须包含：变更原因、受影响需求/设计/代码/测试、风险分析、回归范围、审批记录和新基线标识。任何需求变更都必须触发追踪影响分析。

## 4. 评审规则

评审记录至少包含：评审对象和版本、入口条件、参与角色、问题清单、问题等级、责任人、截止时间、关闭证据和评审结论。

涉及下列内容时必须有领域专家或授权责任人批准：

- PLDS 需求基线及派生需求；
- 安全性/可靠性/抗辐射策略；
- 顶层架构、时钟复位、跨时钟域和关键状态机设计；
- IP 核选择与使用限制；
- 约束文件及豁免项；
- 关键 EDA 操作、失败后的策略变更；
- 验证充分性结论、位流发布和最终交付。

## 5. 仓库约定

- Markdown 是可审阅的工程源文件；PDF/DOCX 是评审或交付快照。
- 图表源文件与导出文件同库保存，图表必须有编号和来源。
- 需求、风险、问题和决策使用稳定 ID，禁止通过改标题重用 ID。
- 机密信息、密钥、真实敏感工程数据不得进入非受控仓库。
- 所有外部标准只记录元数据和内部受控位置，不复制超出授权的内容。
