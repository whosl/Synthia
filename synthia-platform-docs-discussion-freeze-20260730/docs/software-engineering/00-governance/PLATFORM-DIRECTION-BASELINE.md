## 1. 平台目标

Synthia 是面向 FPGA 工程的智能体操作平台，不是 Vivado 或其他 FPGA 工业软件的替代品，也不是单一 RTL 生成器。平台应支持：

1. 接收原始需求、任务书及适用工程资料；
2. 通过受控 Agent 和 Skill 完成需求理解、设计辅助、RTL/测试/约束候选生成和工程分析；
3. 在用户授权范围内，通过 Vivado Connector 调用 Vivado 的 Tcl/API 能力，完成仿真、综合、实现、码流生成等工业软件任务；
4. 将工具执行、原始日志、报告、输出制品和结构化诊断返回给用户，并保留可追溯的运行记录；
5. 允许用户不直接打开 Vivado，通过 Synthia 完成授权范围内的 FPGA 开发任务；
6. 不复制 Vivado 的 GUI 和工程业务逻辑；用户也可以随时回到 Vivado 的传统操作方式，Synthia 不得未经明确授权接管、修改或影响传统工程操作；
7. 未来支持独立 Web 前端和嵌入 FPGA 工业软件的小窗/WebView 两种交互形态，二者共享同一后端 API 和权限边界。

## 2. 标准边界

GB/T 33781/GJB 9432 的过程范围按完整 PLDS 生命周期理解，覆盖系统需求、PLDS 需求、设计、编码及工程实现、确认测试、验收交付、运行维护和支持/管理活动。多 Agent 内容生成的责任边界可位于 B2，但 B2 后的 Vivado 活动仍属于同一过程和证据链。

当前标准文件不完整，只能支撑临时过程设计和监控。正式声明符合 GJB 9432-2018 前，必须取得完整授权文本并由质量/标准化角色逐项复核、裁剪和审计。

## 3. 总体架构方向

采用“Synthia UI（独立或嵌入）/Workflow/Agent + Synthia Core + 厂商无关 Connector Port + 可替换协议 Adapter + 独立 Connector Worker”：

- Synthia UI 负责项目、需求、文档、追踪、差异审查、人工批准、风险、问题、配置和证据导航；UI 可以独立运行，也可以作为 FPGA 工业软件内的小窗或 WebView，不因此取得直连数据库或 Connector 的权限；
- Workflow Engine 拥有 G0～G9 流程状态，Orchestrator 只拆分和路由任务；
- Synthia Core 是工程域元数据、快照、批准、基线和追踪的事实源，不包含 Vivado 命令细节；
- Core 通过厂商无关 Connector Port 调用执行层，MCP/HTTP/Queue 只是可替换 Adapter；
- Vivado Connector Worker 在受控 EDA 主机执行工具/器件发现、仿真、综合、实现、报告、码流、下载和在线调试，并采集原始证据；
- Board/Lab Connector 独立负责串口、外部激励、电源、仪器和板卡资源；
- Agent Skill 固化任务规划、Vivado 能力使用方法、前置条件、输出和风险；Skill 不绕过 Core/Connector 授权，也不把任意 Tcl 直接交给 Worker；
- 工业软件集成只提供上下文、页面和任务入口；所有工程命令仍经 Core/Workflow/Connector 的受控链路提交，传统工业软件操作不受 Synthia 未授权干预。

## 4. 黄金阶段门

| 门 | 批准对象 | 主要结果 |
|---|---|---|
| G1 | 系统需求 | 批准阶段结果；建立 B0 系统需求基线 |
| G2 | PLDS SRS 和派生需求 | 冻结的批准阶段结果，不新增 B 编号 |
| G3 | 结构设计和详细设计 | 批准阶段结果；建立 B1 设计输入基线 |
| G4 | RTL、TB、约束草案和代码审查 | 批准阶段结果；建立 B2 RTL 基线 |
| G5 | 综合和网表结构 | 冻结的批准阶段结果，不新增 B 编号 |
| G6 | 布局布线、DRC、STA | 冻结的批准阶段结果，不新增 B 编号 |
| G7 | 确认测试 | 批准阶段结果；建立 B3 验证基线 |
| G8 | 码流、板测和配置审核 | 冻结的批准阶段结果，不新增 B 编号 |
| G9 | 验收交付 | 批准阶段结果；建立 B4 产品基线/交付包 |

不存在“候选基线”。候选成果先冻结为 `ConfigurationSnapshot` 并通过 `GateSubmission` 提交；人类批准后形成 `ApprovedGateResult`，只有里程碑门建立 B0～B4。Agent 只能创建或修改 `candidate`，只有具有相应权限的人类可以作出批准、拒绝、豁免、基线和验收决定。

工具运行分为 `exploratory/gate_check/formal`：探索运行不进入门禁；门禁检查只绑定冻结提交快照；正式运行只使用批准输入。工具 `succeeded` 不等于工程门批准。

## 5. RT-UART 定位

RT-UART 不再作为平台主规格继续优先深化。它作为：

- 第一条黄金参考项目；
- 文档、追踪、代码和测试模板来源；
- 多 Agent 正向/负向评测集；
- Vivado Connector 回归样例；
- 模拟知识库和端到端演示项目。

知识检索默认只使用已批准成果。草案、错误方案、故障注入样本和失败运行进入历史库或评测集，并以明确标签隔离，不作为正确知识返回。

## 6. 当前优先级

优先评审 `SYNTHIA-GOV-003`、平台总体架构、领域/状态模型、数据存储、API/事件，以及修订后的黄金流程、制品契约、阶段门、Agent 权限、追踪模型、Connector 契约和 MVP 验收计划。Agent Skill、Vivado 能力目录和独立/嵌入式 UI 契约作为实现输入；不把 RT-UART 的特定决策提升为全平台默认规则。

## 7. 两条配置空间

| 配置空间 | 内容 | 关系 |
|---|---|---|
| Synthia 平台 | 独立或嵌入式 UI、Workflow/Agent、Synthia Core、策略/门禁、追踪、知识库、Skill、Connector Port/SDK/Adapter/Worker | 提供智能体交互和受控工业软件操作 |
| 目标 PLDS 项目 | 项目需求、设计、RTL、验证、Vivado 结果、码流、板测和交付证据 | 黄金流程的实例 |

两者分别版本化、测试和发布。平台升级不得静默改变已批准 PLDS 项目的流程、门禁或证据解释。
