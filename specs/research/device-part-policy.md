# 器件（part）策略设计笔记：自由项目不锁器件

- 日期：2026-09-30；来源：T3 jpegencode 160T 对照实验（p29/p30）的复盘讨论
- 状态：已在当前工作区实现并做本地验证；尚未合并部署或执行生产迁移

## 原则（用户裁决）

**平台只分两类项目：自由项目 / 工程项目。没有「基准类」这个平台概念。**

- 基准/盲测/黄金对照属于自由项目的一种**用法**，不是项目类型。它的器件与
  任务书契约（冻结考卷、一条时间线一份考卷）由**操作者手动维护**——是纪律，
  不是机制。平台不为它做冻结开关。
- 自由项目：项目信息（器件、约束、目标频率、名称等）**全面开放编辑**，
  配套配置纪元（epoch）机制保证证据链不撒谎。
- 工程项目：走自己的正式流程契约（门禁/审批），不在本笔记范围。

器件锁死从来只是推样例期的操作约定；纪元机制恰好让「手动维护契约」变得
安全——改了器件，后果是确定的、诚实的（旧证据自动降为历史、徽章回落），
所以不需要平台强制锁。

## 实现前现状：器件活在三层，只有一层用户可见可改

| 层 | 现状 | 问题 |
|---|---|---|
| 任务书（task descriptor） | 创建时带 `part`，explicit-start 后随 descriptorHash 冻结 | 自由项目也被连带冻结 |
| job 的 `part` 字段 | 每次提交自带 | 事实上已是逐单机制，只是被 worker 挡住 |
| worker 绑定 | 66 机 `vivado_part` 单值，全平台一个槽 | 全局串行切换；漂移即 FORMAL_BINDING_MISMATCH（p30 job-41de643a、p28 会话各中过一次）；切器件是操作者 SSH 级动作 |

净效应：用户在产品内没有任何改器件的路径；每个「同源异器件」实验都要操作者
手工克隆项目 + staging（p29/p30 即此产物，约 5 分钟/次）。

## 目标设计

1. **worker 多器件策略**：支持明确器件列表与 `any` 模式；两种模式下，每个
   job 都必须携带明确的 `part`，Worker 按该 job 的器件执行。消除全局单值
   器件限制导致的误拒绝，保留输入、身份与工具链绑定不一致的拒绝检查。
2. **自由项目 part 全面可编辑**：`part` 是项目元数据；项目空闲时修改立即
   生效，运行期间拒绝修改验证配置，不保存待生效配置。job 仍逐单带 part，
   默认取对应回合绑定的项目配置快照。
3. **产品面**：项目设置全面开放编辑（器件/约束/频率/名称）；状态徽章按
   「当前纪元证据」计算；历史 job/报告在时间线上按纪元分段呈现。不做
   「克隆到器件 X」。

## 配置纪元（epoch）模型：改信息 ≠ 丢历史，但历史不再算「已通过」

自由项目随便改，但**验证状态只对当前配置负责**：

- **纪元产生**：验证相关字段（part/约束/目标频率）每次变更，项目配置纪元
  `config_epoch` 前进一格（名称/描述等展示字段不产生纪元）。改回旧配置仍产生
  新纪元，不复用旧纪元的通过状态；保存未变化的配置不产生新纪元。
- **证据归属**：job 提交时打上当时的 `config_epoch`。旧纪元的 job 与报告
  （含 baseline-summary）**自动降为历史版**——可查看、可追溯，但不再计入
  「当前已通过」状态。
- **配置快照**：每个纪元保存不可变快照，包括 part、约束内容或内容哈希、
  目标频率、修改人和时间。约束哈希必须对应可追溯的不可变内容，仅保存可变
  文件路径不足以标识配置。job 提交时由 Core 绑定纪元与快照，不信任调用方
  自行声明的纪元；执行结果和报告沿用提交时的归属。
- **状态语义**：项目「四步全绿」徽章 = 当前纪元下存在同一有效验证链。
  链内要求相同源码快照，并保持顶层、测试、约束输入及各阶段依赖关系一致；
  不得将互不关联的四次成功拼成通过链。各操作的输入哈希可以不同，但必须
  能追溯到同一链的配置与输入快照。改完器件，
  徽章自动回落为「待验证」，直到在新配置下重跑——不需要人工作废任何东西，
  也不需要克隆新项目。
- **实现口径**：降级用**读取时派生**（view 层按 `job.config_epoch` 与项目当前
  纪元比对）而非回写 job 记录。旧证据始终保持历史归属；即使改回相同配置，
  也必须在新纪元重新验证，不自动恢复旧证据的当前有效性。
- **统一读取规则**：通过徽章、时序和资源摘要、baseline-summary 都按当前
  纪元及有效验证链读取；历史报告仍可单独查看，明确显示其纪元或归属未知。
- **并发约束**：仅项目空闲时允许修改验证配置；项目有运行中 Agent 回合、
  排队或执行中 job，或执行结果尚未确认的 job 时拒绝修改。具体并发契约见下节。
- **基准用法的纪律落点**：做盲测/对照时，操作者发车后**不动**器件与任务书；
  万一动了，纪元分段会如实呈现「这份证据属于另一份配置」，实验记录仍然
  可信——纪律失误不演变成数据撒谎。

## 治理边界（改器件不等于放开口子）

- 用户/项目主可改自由项目的 part；agent 仍只能逐单提交 part，且必须符合
  Worker 器件策略——该策略是**运维资源边界**（licence/机时），不是实验控制。
- 基准契约不进平台机制：要保证「一份冻结考卷对一条完整时间线」，操作者
  自己不改就行；平台只保证改了必留痕、旧证据必降级。

## 配置编辑与并发契约（用户裁决）

- 验证配置包括器件、约束和目标频率。只有项目无运行中 Agent 回合、无排队
  或执行中的 job，且无执行结果尚未确认的 job 时，才允许修改；不能仅根据
  主 Agent 处于等待输入状态判断空闲，项目下的其它回合和后台 job 同样计入。
- 运行期间修改验证配置明确拒绝，并返回阻塞的回合或 job；页面说明具体
  原因及何时可以修改，不排队保存，不维护“待生效配置”。名称、描述等展示
  字段可随时修改，不产生新纪元；同时提交展示和验证字段时，验证配置检查
  失败则整次修改拒绝，不静默部分保存。
- 空闲时修改成功立即生效，创建新的不可变配置快照并前进纪元。下一回合
  读取并绑定新配置；已完成回合的任务书、旧 job 和报告保留原快照，不回写
  历史 descriptor。持久 Project Agent 会话应按回合刷新配置，而非永远沿用
  会话首次创建时的器件。
- 配置更新、回合启动和 job 提交统一经过 Core 并发检查，并在短事务内取得
  同一项目行锁。检查活动状态、绑定配置快照或登记活动占用应在事务中完成，
  提交后再调用 Runtime/Connector；不可在“检查为空闲”与登记之间留下窗口。
- job 必须使用所属回合绑定的配置快照；直接提交的 job 在登记时绑定当前
  配置。已经登记的排队 job 也阻塞配置修改，不能在队列执行时重新读取项目
  当前值。提交失败、取消或完成时按真实状态释放占用；执行结果未确认时
  保留占用，待核实终态后才能修改配置。
- 配置编辑请求携带预期纪元或配置修订号；Core 拒绝过期请求，避免两个
  编辑者覆盖彼此的修改。展示字段修改不递增配置纪元，但仍需防止编辑覆盖。

## Worker `any` 与逐单器件契约（用户裁决）

- 列表模式：只接受列表中的具体器件。`any` 模式：不设运维器件允许列表，
  但仍受本机 Vivado 安装的器件目录、license 和既有执行权限约束。
- `any` 只用于 Worker 策略，不能作为 job.part 的值。Core 在提交 job 前将
  项目配置中的默认器件解析成具体 part，并绑定对应配置快照；无法解析则
  拒绝提交。Worker 收到缺失、空值或 `any` 器件的 job 也应拒绝。
- 请求中的 part、嵌套工具链 part 和配置快照必须一致。Worker 必须按 job.part
  执行并在结果中记录实际器件，不能覆盖成 Worker 全局默认值，也不能静默
  回退到另一个器件。输入哈希、工具链身份及正式流程绑定检查继续保留。
- 器件不在允许列表、器件未安装、license 不可用和请求绑定不一致应分别报告，
  使操作者能够区分资源限制与请求错误；`any` 不承诺所有器件均可执行。
- 从 Connector TypeScript 源码修改配置校验、能力发现、请求绑定和 Vivado
  adapter 的器件选择，测试后重新生成 bundle。多器件支持不改变执行并发度。

## 迁移与旧证据处理（用户裁决）

- 自由/工程项目分类不变，现有项目无需类型转换；新增配置纪元、不可变快照
  和 job 归属仍需数据库迁移及旧数据处理。
- 只有能可靠确认配置及输入归属的旧 job 才能归入对应初始化纪元；计入当前
  通过状态还必须满足当前配置及完整验证链要求，不能仅按项目 ID 批量认定。
- 无法确认配置或曾混用器件的旧证据保留为历史、归属待确认，不自动计入
  当前通过徽章。不得把所有旧 job 默认绑定到当前配置。
- 先建立配置快照和证据归属，再完成 Worker 多器件支持、项目编辑接口及页面
  展示，避免开放修改后仍按旧规则显示通过状态。

## 实现落点

- `connector/server.ts` / `connector/vivado.ts`：Worker 列表/any 策略及逐单
  器件执行；同步配置与发现契约，重新生成 `connector/server.bundle.mjs`
- `core/src/api/handlers.ts` / task-proxy：自由项目 part 可变 + 变更事件；
  项目行锁保护配置编辑、回合启动和 job 登记；job 落库时绑定 `config_epoch`
  与不可变配置快照；项目当前纪元变更即前进，Project Agent 按回合刷新配置
- web：项目设置全面开放编辑；状态徽章按当前纪元计算；时间线按纪元分段
- 迁移：新增纪元、快照与 job 归属并保守处理旧证据；项目类型不变，其基准
  纪律继续由操作者手动维持

## 本地实现记录（2026-09-30）

- 数据库迁移 `0039_project_configuration_epochs.sql` 新增配置纪元、设置修订号、
  不可变配置快照与任务/job 归属。现有自由项目建立初始配置，既有 job 保持
  `config_epoch=NULL`，显示“配置归属待确认”；没有把旧证据批量认定为当前。
- `GET/PATCH /api/v1/projects/:id/settings` 提供设置读取、实际活动阻塞原因、
  预期修订号校验、同值保存与幂等重试。新自由项目自动赋予创建者 owner；旧
  项目已有 owner 可编辑，尚无 owner 的项目由管理员编辑或明确分配 owner。
  工程项目的验证配置继续走正式流程。
- 配置修改、主 Agent 下一回合登记、侧任务创建及 job 提交使用同一个项目锁。
  Project Agent 下一回合携带器件、频率、约束快照，重建工具上下文并保留会话；
  原始任务书器件和 descriptor hash 不回写。停用 Core-owned task lifecycle 的
  旧部署只开放名称/描述编辑，防止 Runtime-only 活动绕过空闲检查。已在运行的
  未登记旧 Runtime 会话也会阻塞修改；无法确认 Runtime 活动时暂停验证配置
  编辑。现代自由项目的旧会话不能从 legacy message 路径启动新回合，需要使用
  Core-owned Project Agent 继续，历史读取与终止仍保留。
- job 登记后再派发到 Connector。丢失响应时保留 `unknown_effect` 和原始输入，
  使用相同 job ID 修复派发；缺失 Worker 记录的自由项目 job 保留 `lost`，仍阻塞
  配置修改。只有可信终态或明确的执行前拒绝才释放活动占用。
- 当前摘要过滤纪元、设计输入指纹、顶层和约束；能够识别的独立 testbench 与
  RTL 设计分开记录，允许 RTL-only 综合与包含 TB 的仿真衔接。通过链必须按
  validate → simulate → synthesize → implement 的依赖顺序完成；前置验证更新后
  旧下游结果标记为 stale 并要求重跑。频率字段不会凭空生成端口/时钟约束；
  实际时序要求由保存的 XDC 表达，目标频率同步提供给 Agent。
- 资源、时序、码流摘要只读取当前归属；历史 evidence 与报告（包括 job 内的
  baseline-summary）读取时返回原配置快照和历史/未知标签，内容保持原样。
  网页提供设置弹窗、忙碌禁用及原因、过期编辑提示、历史配置分段。
- Worker 支持单器件（兼容）、具体器件列表与 `any`；每个执行 job 必须带具体
  器件，并保持嵌套工具链一致。逐单 TCL 和结果 metadata 使用该器件；安装、
  license、输入和工具链身份校验继续生效。已在临时目录生成开发 bundle 并
  完成 Node 烟测，tracked 正式 bundle 与生产 Worker 配置尚未更新。
