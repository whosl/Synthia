# bench-lib T1 重跑（平台修复后）：SHA3-512 盲测 — p14 vs p13

- 日期：2026-09-09/10
- 前置：T1/aes（p11/p12）暴露的两个平台问题（P1 传输断连整轮报废、P2 Core 转发挂死）已修复并提交（3ad1207 / f710c7b / e63161b），本实验在修复后的栈上重跑 T1
- 基准件：`golden/bench-lib/sha3`（FreeCores，Apache）
- 需求：FIPS-202 提炼 v1.1（DRQ 编号，零结构信息；字节流接口，I/O=13）
- 协议/模型与 p5-p12 一致

## 1. 模板制作中的三次需求级/工程级修正（再次验证"黄金基线先行"）

1. **上游核心是原始 Keccak 而非 SHA3**：上游 keccak.v 的填充是 0x01..0x80（其自带 KAT d135bb… 即 Keccak 遗留值），SHA3 需 0x06 域分隔。黄金封装改为直接以参考的 `round`+`rconst`（纯组合单轮+轮常量，算法黄金本体）自建 24 轮海绵控制器。
2. **f_permutation 握手在 XSim 下死锁**：其 `#1` 延迟 + one-hot 移位握手在 iverilog 通过、XSim 全 X（诊断显示实例内部 calc/i 悬空）。round 基控制器无此问题。**iverilog 预检不能替代 XSim 验证**——AES 时两者一致，本设计暴露分歧。
3. **需求 KAT 常量笔误（出题方错误，非模型）**：狐狸句期望误抄上游 Keccak 值 d135bb…。模型盲测自建参考模型算出正确 SHA3 值 01dedd… 且 DUT 与之一致，却因需求常量错而反复"修"正确实现（第 17-19 轮）。勘误 v1.1 后其原实现直接通过。**教训：需求中的每个常量必须双源验证**（本例 hashlib vs 上游 TB，抄了单源）。

## 3. 结论

1. **平台修复全效**：p12 时的传输断连（整轮报废 + 手工恢复）与 Core 转发挂死在本轮全程未复发；19 轮长交互中 agent 从未因平台原因中断。
2. **模型从规范实现 Keccak-f 成功**：GLM 独立写出 24 轮置换 + 海绵结构并四步全绿；资源/时序全面优于黄金基线（LUT 4249 vs 4930，WNS +2.76 vs +1.35）——参考实现的 one-hot 轮选择器面积较大，模型的实现更紧凑。
3. **19 轮收敛的构成**：1 轮语法（TB 引号/bit 类型）+ 15 轮真实功能迭代（探针方法学出色：PROBE 场景逐步缩小到 2 字节填充边界）+ 3 轮被需求笔误误导。**剔除出题方错误后实际功能收敛 ≈ 15 轮**，与设计难度（Keccak 从零实现 > AES）相称。
4. **黄金基线先行第三次救场**：KAT 常量错误若未在黄金侧发现（本例是盲测侧自建参考模型暴露的——模型自己的参考实现成了第二真相源），盲测会被迫"修复"正确实现。**双源常量验证**入模板制作红线。

## 4. 度量口径与证据

- p13 证据：四步全绿（implement sta/resources 落盘）；本地 iverilog + 远端 XSim 双验证
- p14 证据：19 次仿真 job 演化链（语法→功能→勘误后确认）；KAT 全场景 PASS；需求勘误 v1.1 登记可溯
- 输入哈希：v1.0 `cffeea59…` → v1.1 勘误（agent 侧全程可追溯）
