# bench-lib T1：AES-128 盲测 — Synthia（GLM）vs 黄金基线（p12 vs p11）

- 日期：2026-09-09
- 基准件：`golden/bench-lib/aes_core`（FreeCores 参考实现， LGPL 类，内部基准用）
- 需求：FIPS-197 提炼的 `doc/01-开发技术要求.md` v1.2（DRQ 编号，零结构信息；字节流接口）
- 协议：p5-p10 盲测协议；输入哈希 `19c30f3e…` 双侧一致；part xc7k70tfbv676-1；worker 66 Vivado 2021.1
- 模型：GLM-4.6（智谱 Anthropic 端点，64k 预算）

## 0. 模板制作中的两次需求级修正（流程验证的价值）

T1 的目的就是把模板制作流程走通，两次踩坑都是需求文档层面的、且在盲测发车前修掉：

1. **复位极性**：初版需求写"高有效"，参考实现是低有效（`if(!rst)` 复位）——黄金基线 TB 第一轮就暴露。修正需求 v1.1 对齐。
2. **I/O 预算**：初版接口是全并行 128 位（key/text_in/text_out），共 388 个 I/O——超出 fbv676 封装可用引脚，implement 物理不可布（Place 30-415 overutilization）。修正 v1.2 改字节流接口（32 字节装载/16 字节流出，I/O=22）。**红线复查**：两次修正均未引入结构信息（极性是接口契约、字节序锚定 FIPS 附录 A）。

黄金基线侧为此增加 `rtl/aes_top.v`（字节流薄封装，黄金自有）+ TB v3（C.1 KAT + 8 组 openssl 互验随机向量 + B2B + 忙窗干扰）。**iverilog 本地预检 + XSim 双过**。

## 2. 结论

1. **T1 流程验证通过**：aes 上完整走了"需求提炼 → 黄金基线（参考 RTL + 自检 TB + 四步指标）→ 盲测 → 对比"，两次需求级缺陷（复位极性、I/O 预算）都被黄金基线侧提前暴露并修正——**黄金基线先行的价值得到直接证明**（盲测发车后改需求就晚了）。
2. **模型侧表现**：GLM 从纯规范独立实现 AES-128 并四步全绿（仿真一次修复收敛：先失败一次、用 logDigest 定位后修复）。时序与人工参考同量级（WNS 差 0.016ns）；资源 3.4×/2.4× 超出参考但仍远低于需求预算（LUT≤6000/FF≤2500）——参考实现是高度优化的手工代码，资源差距属预期形态。KAT 精确匹配（C.1 + 随机向量）证明功能正确性无妥协。
3. **新的平台观察（T1 期间）**：
   - **模型传输断连致整轮报废**：GLM 端点 socket 断连 → agent 直接 failed（endedReason 记录），无传输层重试；且 **Core 的 task-proxy 消息转发在 agent 恢复态挂死**（>100s 无响应，绕过 Core 直打 Runtime 秒通）。两者都值得进 harness 清单（分别类比 H3/H1 的精神：失败要可恢复、转发不能黑洞）。
   - 大上下文长思考下 GLM 单轮可达 16+ 分钟（AES 轮函数生成），64k 预算无空回复（H3 守卫未触发）。
