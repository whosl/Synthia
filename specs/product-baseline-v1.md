# Synthia 产品基线 v1

- 状态：已定稿；作为后续规格和实现的上位依据
- 确认日期：2026-08-20
- 适用范围：首个可供个人长期使用、并可进入组织试用准备的版本

## 1. 产品是什么

Synthia 是面向 FPGA 工程开发的 AI 工程平台。它既能按 GJB 等工程流程维护需求、设计、RTL、验证、证据、阶段确认和交付，也能作为自由的 Coding Agent 加 FPGA 技能工具，处理排错、修改、试验和其他临时工作。

首版工程流程为 **GJB 参考流程 v1**。它参考仓库已有工程资料，但不代表平台已经取得 GJB 9432-2018 符合性；正式符合性仍需完整授权标准和项目裁剪依据。

这是面向个人使用的精简流程：G4 同时包含 RTL、仿真、综合、实现、DRC、时序、正式码流和交付包。仓库现有的 G0～G9 流程保留为以后面向组织的完整流程参考，不作为首版完成线。

### 首版 G0～G4

| 阶段 | 用户能理解的目标 | 最低完成条件 |
|---|---|---|
| G0 项目准备 | 把项目边界和工具准备好 | 项目类型、流程版本、数据范围、器件/板卡状态、来源资料和工作区已记录 |
| G1 需求确认 | 说清楚要做什么 | 需求来源明确、接口和验收目标可检查、关键风险有处理办法 |
| G2 行为与验证方案 | 说清楚应该怎么工作、怎么证明它正确 | 功能/性能/时序/异常行为明确，验证方法和需求对应，无关键遗漏 |
| G3 设计确认 | 说清楚怎么实现 | 架构、接口、寄存器、时钟复位、约束策略和关键边界足以指导编码 |
| G4 实现与交付 | 产出可以追溯的正式结果 | RTL、TB、约束齐全；仿真/综合/实现完成；DRC 无错误、时序达标；正式码流和交付包与同一不可变输入快照绑定 |

G4 之前可以运行探索性工具任务。只有用户确认过输入文件和运行用途，且满足上表条件的结果，才能作为正式 G4 证据。板卡、引脚或电气约束不完整时只能生成试验码流，不能完成正式 G4。

## 2. 两类项目

创建项目时必须选择类型：

- **自由项目**：只要求项目名称，器件可后选；不强制阶段、文档、确认或里程碑。
- **工程项目**：必须选择一个有版本的流程，首版只有 GJB 参考流程 v1；建议创建时选择器件，板卡、引脚和电气约束可稍后补齐，但在正式 G4 前必须补齐适用约束。

项目创建后不自动改变类型或流程版本。流程升级由用户主动发起并保留记录。自由项目需要正式化时，复制为新的工程项目，并记录来源关系，不在原项目上直接切换。

## 3. Agent 与工作方式

用户看到的是一个项目、一个主对话，以及类似 Codex 的侧边聊天/任务。主 Agent 可自动派侧边任务，用户也可手动创建。

自由项目可同时开展任意数量的任务。文件修改前，用户先授权一组工作范围；超出范围、可能覆盖已有修改或发生冲突时，平台再次询问。

工程项目始终只有一条正式推进线。侧边任务只能在独立的临时副本中查资料、改文件、编译和仿真，并把结论、改动说明和测试结果返回主对话。只有用户确认后，主 Agent 才能把选中结果作为新的候选内容放入正式项目；未经确认的侧边结果不能参与阶段确认。主 Agent 等待当前阶段确认时，侧边任务可以提前准备后续工作。

## 4. 历史项目知识库

工程项目可导入另一个 Synthia 项目，或本地目录/ZIP；Git 仓库导入首版暂缓。每次导入都是固定快照，来源变化不会自动同步，更新必须由用户主动发起并形成新版本。

- Synthia 内部资料默认只检索“已确认且仍有效”的版本。
- 外部资料先标为“待确认”，确认后才进入 Agent 的默认参考范围。
- 草稿、被否决或失败的资料不默认推荐；用户主动查看时必须标明其状态。
- 支持只查阅，也支持复制选中内容。复制内容成为当前项目的新候选，不继承原来的确认状态。

默认导入 Verilog/SystemVerilog、测试平台、XDC/Tcl、Markdown、纯文本、PDF、JSON 和 YAML；忽略缓存、中间文件、普通大日志、`.env`、密钥和证书。码流、DCP 和正式报告由用户选择是否保留。VHDL 首版只保证导入、查看和参考。

## 5. 阶段确认、执行与交付

首版面向单个 FPGA 工程师，工程师本人兼任开发者、评审者和项目负责人，可以确认自己的阶段成果，但生成身份与确认身份仍分别记录。保留登录，不做注册、邀请、成员管理或权限页面；数据模型预留 owner、member 和 permission。

Agent 可以自动运行编译、仿真、综合和试验性实现。若结果要用作正式里程碑证据，平台必须先列明将使用的输入文件并取得用户确认。未来的上板、下载和烧写必须每次单独确认。

首版工程项目的完成条件是：通过精简流程的 G4，并生成可追溯的正式码流和完整交付包。正式 G4 至少要求完整约束、DRC 无错误、时序达标，以及绑定同一不可变输入快照的证据。缺少完整板卡、引脚或电气约束时可以生成“试验码流”，但不能通过正式 G4，也不能作为正式交付。

交付包至少包含 RTL、约束、测试平台、文档、运行结果、原始证据、确认记录、版本来源和码流。当前没有上板条件，上板测试不纳入首版 G4，但必须列入后续路线图。正式完成后如需修改，必须经过“发起变更 → 新工作版本 → 重新验证 → 新正式版本”。

## 6. 数据保全与工程边界

首版必须支持完整备份和恢复，包括项目与 Git 历史、候选和已确认版本、里程碑、本人确认记录、主对话与侧边任务、Vivado 任务与证据、历史导入及来源、流程版本和必要配置。模型密钥、Connector 凭证、证书和缓存不进入备份包，恢复后重新配置。

项目类型、流程、知识库、侧边任务和正式采纳由 Core/Runtime 管理。多任务不需要增加 Connector 类型或修改 `connector.remote.v1`；Connector 只执行已经过 Core 判断的工具任务。

## 7. 首版之外与上线前必修

首版暂不做：其他标准的具体流程、Git 导入、多成员协作、用户管理、可靠的 VHDL 生成/修改/完整验证，以及真实上板、下载和烧写。

组织试用前必须修好 Connector 的项目归属校验、请求参数绑定、并发注册竞态、任务与幂等状态持久化、真正停止 Vivado 的取消机制、UUID 项目 ID 兼容、正式运行与不可变快照/输入哈希/有效基线绑定、占位 manifest，以及数据分类映射。

## 8. 实施顺序

1. 项目类型、流程模板/版本及创建入口。
2. 历史资料导入、状态标注、检索和复制。
3. 侧边任务、临时工作区、结果回传和正式采纳。
4. 精简 G0～G4 推进、正式证据、码流和交付包。
5. 备份与恢复。
6. Connector 组织试用前可靠性修复。

现有 `specs/001-agent-freedom/` 和 `specs/projects-page-v4.md` 是较早的功能/界面规格。凡与本文件冲突，以本基线为准，并在对应实施切片开始前同步修订。
