# Synthia v1 实施计划

- **上位依据**：[`product-baseline-v1.md`](./product-baseline-v1.md)
- **状态**：可进入实施
- **目标**：把已确认的产品方向拆成可逐片交付、可回滚、可验收的软件工作
- **原则**：每个切片都必须同时有 Core/API、Runtime 接缝、Web 主路径、测试和文档；不接受只有页面占位或只有数据库字段的“完成”。

## 1. 团队分工

首版虽然是单人使用的产品，开发仍按小型软件团队分工。一个人可以兼任多个角色，但每个切片要有明确的实现者和复核者。

| 角色 | 主要职责 | 主要目录/产物 |
|---|---|---|
| 产品与架构 | 维护产品基线、冻结数据契约、处理跨模块取舍 | `specs/`、状态图、API 契约 |
| Core/数据 | 数据库迁移、状态机、API、幂等、审计和跨项目隔离 | `core/src/domain/`、`core/src/db/`、`core/src/api/` |
| Runtime/Agent | 主对话、侧边任务、授权范围、临时工作区、上下文和恢复 | `runtime/` |
| Web | 项目创建、工作台、资料库、差异/采纳、阶段和证据展示 | `web/src/` |
| Connector | Vivado 任务执行、取消、注册、证据和正式输入绑定 | `connector/`、`core/src/api/connector-adapter.ts` |
| 质量与发布 | 契约测试、端到端测试、迁移/恢复演练、组织试用门槛 | `core/tests/`、`runtime/*.test.ts`、`web/tests/` |

开发协作约定：分支使用 `codex/` 前缀；每个切片单独提交，提交说明遵循 Conventional Commits；合并前必须附验证命令、已知限制和回滚办法。产品基线与本计划发生冲突时，先停下同步文档，不在代码里自行猜测。

## 2. 当前起点

已经可以复用：三栏项目工作台、工作区读写/登记 API、自由 Agent 会话、SSE/轮询任务流、现有门禁/审批/证据模型，以及 Core 对 `exploratory`、`gate_check`、`formal` 的初步授权判断。

尚未形成闭环：项目类型和流程版本、G0 准备状态、历史资料快照和检索、主/侧任务关系、隔离副本与采纳、精简 G0～G4 的正式证据和交付包、Core 中的会话事实、完整备份恢复，以及 Connector 的组织试用级可靠性。

## 3. 阶段总览

依赖关系为：

```text
P0 契约冻结
  ↓
P1 项目模型与创建
  ├──→ P2 历史资料库
  └──→ P3 主 Agent / 侧边任务 / 采纳
          ↓
       P4 精简 G0～G4、正式证据与交付
          ├──→ P5 备份恢复与变更闭环
          └──→ P6 Connector 可靠性
                    ↓
                 P7 组织试用门槛
```

P2 和 P3 在 P1 的数据契约稳定后可以并行；P5 和 P6 在 P4 的正式输入契约稳定后可以并行。每阶段结束都要有可演示的主路径。

## 4. 分阶段实施

### P0：架构与契约冻结

**目标**：先把以后最容易反复改动的概念定死。

- 定义 `project_type=free|engineering`、不可变 `process_version`、项目配置（器件、板卡、引脚、电气约束完整度）。
- 定义流程注册表；首版只注册 `GJB_REF_V1`，只开放 G0～G4。旧 G0～G9 枚举保留兼容，但不能被首版 UI 默认使用。
- 定义任务 `main|side`、父任务、临时工作区、授权范围、结果包和采纳记录。
- 定义导入快照、来源、资料状态（待确认/已确认/仍有效/被否决/失败）。
- 定义正式运行的唯一输入：不可变快照、active 里程碑、manifest、文件哈希、工具链/器件/约束完整度。
- 定义交付包和备份包的 manifest 版本；秘密、证书和缓存明确排除。

**交付物与退出条件**：数据字典、状态图、JSON/API 示例、旧数据兼容策略、迁移顺序和跨服务 fixture；Core、Runtime、Web、Connector 负责人共同签字后才能进入 P1。

### P1：项目类型、流程版本与创建入口

**目标**：用户创建项目时就得到正确的项目类型和流程边界。

**Core/数据**

- 新增 `process_definition/process_version`，并新增 `project.project_type`、`project.process_version_id`、项目约束状态字段。
- 建议迁移：`0006_project_type_process_version.sql`、`0007_project_profile_constraints.sql`。
- 工程项目必须选择有效流程版本；自由项目只要求名称，器件可为空。
- 流程版本创建后不可静默替换；升级必须由用户主动发起，记录迁移结果，旧项目继续使用原版本。
- 创建时幂等建立 G0 准备记录；旧项目回填兼容 profile，不静默改成新流程。
- 增加 `GET /process-versions`、扩展 `POST/GET /projects`，并提供“复制为新工程项目”接口。

**Web/Runtime**

- `ProjectListView` 新建向导先选自由/工程；工程项目再选 `GJB_REF_V1` 和器件。
- 项目详情显示类型和流程版本，创建后不可直接切换；自由转工程只能复制。
- Runtime 根据项目类型选择自由会话或工程主线，不再用旧默认 GJB 流程兜底。

**验收**：两类项目都能创建、刷新后字段不变；工程项目缺流程被拒绝；自由项目不显示强制阶段；重复请求不产生重复项目或流程实例。

### P2：历史资料库

**目标**：工程项目能安全地参考历史项目或本地资料。

- 建议迁移：`0008_import_snapshots.sql`，包含快照、来源、文件条目、确认状态和来源哈希。
- 首版支持 Synthia 项目、本地目录和 ZIP；不做 Git 仓库导入。
- 实现固定快照、路径安全、压缩包大小/条目限制和敏感文件排除。
- 提供导入、查看、搜索、确认/否决、复制选中内容 API；默认搜索只返回已确认且仍有效的资料。
- 复制到当前项目时创建新候选版本，不继承原确认状态；写入来源关系和审计事件。
- Runtime 的 `context-snapshot` 只消费默认可检索资料；自由项目不被强制接入资料库。

**验收**：导入→待确认→确认→可检索→复制为候选的链路完整；外部资料未确认时不会进入 Agent 默认上下文；路径穿越、ZIP 炸弹、`.env`/密钥/证书和跨项目访问均被拒绝。

### P3：主 Agent、侧边任务与正式采纳

**目标**：用户只看到一个主对话，但可以安全地开展侧边探索。

**Core/Runtime**

- 建议迁移：`0009_task_workspaces.sql`；任务记录至少包含 `kind`、`parent_task_id`、`workspace_id`、授权范围、状态、输入/输出哈希和采纳结果。
- 工程项目同一时间只允许一条正式主线；侧边任务只能使用临时副本，不能提门、建里程碑或启动正式运行。
- 把任务、对话事件和采纳记录写入 Core；`.runs/` 降为缓存/恢复材料，不再是唯一事实源。
- 新增任务副本、差异、结果和采纳 API。采纳必须由用户确认，按选中文件复制为当前项目新候选，并检查覆盖冲突。
- 复用现有 SSE、Core 权限和 Connector 类型；侧边任务的工具运行统一标为 `exploratory`。

**Web**

- 主对话旁提供“新建探索任务”；卡片显示目标、状态、临时副本、结论、改动、测试和“采纳选中内容”。
- 采纳前展示路径、差异、哈希和将被覆盖的文件；未采纳结果明确标注，不影响正式阶段条。

**验收**：主线等待确认时侧边任务仍可运行；工程项目不能出现两条正式主线；重启后任务和结果可恢复；跨项目、越权写入、覆盖冲突和重复采纳均 fail-closed。

### P4：精简 G0～G4、正式证据、码流与交付

**目标**：完成首版真正的工程闭环。

- 建议迁移：`0010_process_gate_checks.sql`、`0011_delivery_release.sql`。
- 将阶段链改为 profile 驱动：G0 准备、G1 需求、G2 行为与验证方案、G3 设计、G4 实现与交付；移除 Web/Runtime 对 15 节点和 G5～G9 的硬编码依赖。
- G4 汇总 RTL、TB、约束、仿真、综合、实现、DRC、时序、原始日志和证据；完整约束不足时只能生成试验码流。
- 正式 Job 复用现有 Core `formal` 授权，但必须绑定 approved snapshot、active baseline、manifest/input hash、工具链、器件和约束完整度。
- 交付包包含 RTL、TB、约束、文档、运行结果、原始证据、确认记录、来源、码流及可验证 manifest。
- 正式完成后的修改必须创建变更请求、新工作版本、重新验证和新正式版本。

**验收**：任何缺少快照、输入哈希、完整约束、DRC 通过或时序达标的结果都不能通过 G4；正式码流可追溯且与试验码流清楚区分；本人确认记录同时保留生成身份和确认身份。

### P5：备份、恢复与变更闭环

**目标**：个人工具也能在故障后完整找回工程事实。

- 建议迁移：`0012_backup_archives.sql`；实现版本化备份 manifest、导出、校验、预览恢复和原子恢复。
- 备份包括项目/Git 历史、候选和已确认版本、里程碑、确认记录、主/侧任务、Vivado 任务与证据、导入资料及来源、流程版本和必要配置。
- 明确排除模型密钥、Connector 凭证、证书和缓存；恢复后重新配置并记录审计事件。
- 恢复先进入临时空间，完成哈希、版本和秘密扫描后再切换；损坏或版本不兼容时不得半恢复。

**验收**：完整备份 round-trip 后项目、Git commit、审批、任务和证据一致；损坏包、路径穿越、秘密泄漏和重复恢复都有明确失败结果。

### P6：Connector 组织试用前硬化

**目标**：让多项目、重启和失败场景不会破坏工程事实。

- 建议迁移：`0013_connector_registration_reliability.sql`，但保持 `connector.remote.v1` 协议不变。
- 所有 status/cancel/evidence 请求校验项目归属；外层字段与嵌套 `parameters` 逐字段绑定。
- 用数据库/持久化租约消除多项目注册竞态；Job、幂等键和状态在 Worker 重启后可恢复。
- cancel 必须真正终止 Vivado；无法确认时标记 `unknown_effect`，不能假装取消成功。
- 接受 `proj-<uuid>` 等项目 ID；formal/gate 运行必须绑定不可变快照、输入哈希和 active baseline；去掉 `manifest:<jobId>` 占位输入并修正数据分类映射。

**验收**：跨项目请求被拒绝；并发注册只有一个有效赢家；重放不重复执行；取消能终止进程或明确报告未知效果；UUID 项目能完成端到端 formal 流程。

### P7：组织试用门槛

**目标**：不是“功能看起来能用”，而是可以安全交给真实工程师试用。

- 完整跑 Core、Runtime、Connector、Web 测试和类型检查。
- 做一次真实备份/恢复演练、Connector 重启/断网/取消演练、跨项目隔离演练和正式/试验码流混淆演练。
- 用浏览器走通：创建两类项目、导入资料、开侧边任务、查看差异、采纳、推进 G0～G4、下载交付包。
- 发布前冻结流程版本、API 契约、备份格式和回滚手册；未通过的项进入明确的阻断清单，不以“后续优化”掩盖。

## 5. 回滚与发布策略

- 数据库只做可重放的前向迁移；旧字段和旧接口在兼容窗口内保留读取能力，不直接删除历史数据。
- P1 的新建向导、P2 的导入入口、P3 的侧边任务、P4 的正式运行、P5 的恢复写回和 P6 的新 Worker 生命周期都要有独立开关。开关关闭时，旧的个人验证路径仍可读，但不能伪装成新基线已完成。
- 任何正式 G4、交付包或恢复写回功能，在对应端到端验收完成前只允许 dry-run/试验模式；试验码流永远不能升级成正式码流。
- 发现跨项目越权、快照不一致、秘密进入备份或取消状态不真实时，立即封禁相关写操作，保留只读查询和审计，不回滚或删除已有历史。
- 每个切片发布前准备一条最短回滚路径：关闭开关、恢复上一版 API/Worker、保留迁移数据，并用备份包验证可恢复。

## 6. 第一批可直接开工的任务

第一批只做 P0 + P1，形成一个完整可演示增量：

1. `PB-001`：写项目模型/流程版本契约和兼容矩阵。
2. `PB-002`：新增 `0006/0007` 迁移、Core 类型和创建/查询 API。
3. `PB-003`：为创建、幂等、旧项目回填和 G0 准备状态补 Core 测试。
4. `PB-004`：改造 Web 新建向导和项目详情展示，补 Web 测试。
5. `PB-005`：让 Runtime 按项目类型读取流程版本，补跨项目/错误配置测试。
6. `PB-006`：浏览器走查两类项目创建、刷新和进入工作台，记录截图与已知限制。

第一批的完成标准：新建自由项目和工程项目都能走通；工程项目明确显示“GJB 参考流程 v1”；自由项目不再被旧 GJB 阶段条或默认器件强行约束；全量受影响测试通过。

## 7. 统一 Definition of Done

每个切片合并前必须满足：

- 产品行为与 `product-baseline-v1.md` 一致，旧规格冲突已标注；
- Core API 有输入校验、项目归属校验、幂等键和审计事件；
- 数据库迁移可重复执行，旧数据有回填或兼容说明，`schema.sql` 已同步；
- Runtime 不绕过 Core；正式运行 fail-closed；`.runs` 不承担唯一事实；
- Web 有成功、空状态、拒绝、冲突和恢复后的可见反馈；
- 有 Core/Runtime/Web 相关行为测试，必要时有 Connector 集成测试；
- 执行 `bun test`、Core 类型检查、Runtime 类型检查和 Web 检查/构建；
- 记录演示步骤、风险、回滚办法和下一切片的依赖。

## 8. 计划外事项

本计划不提前实现其他标准流程、Git 仓库导入、多成员协作、可靠 VHDL 生成/修改、真实上板下载/烧写或自动流程升级。这些只能在产品基线新增决定后进入新的版本计划。
